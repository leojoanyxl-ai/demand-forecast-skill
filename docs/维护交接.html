后续维护与交接

适用对象：继续修改本项目的组员或开发者。当前计算案例信息截止2026-11-03，预测2027—2028。项目说明更新不代表重新估计了经济参数。

接手先做三件事

1. 保留下载版本和原输出，阅读组员分享要点、Skill入口与实际验证记录。不要把“程序完成”读成“真实业务通过”。

2. 保持输入不变跑通新能源汽车和ABS，确认自己环境中的结果与交付结果一致，再开始修改。

3. 在GitHub新建修改分支，一次只处理一个明确问题，记录改了什么、证据是什么、影响哪条结果。每次运行使用一个尚不存在的新输出目录。

按修改类型选择验证

修改类型需要做的核查
仅说明文字、排版、交接核对数字、链接、生成后的页面与压缩包内容，不把它写成模型精度提升
只改未来情景或企业假设重跑对应行业和条件核算，确认成立条件、单位及缺数状态；预测变化不应被说成新增实证证据
补历史数据、改口径或参数识别检查连续性、来源、发布时间、版本与实际／估计性质；重新做时间顺序验证和方法比较，解释与旧版差异
改算法、公式、选模或行业适配器补有意义的行为检查，并验证训练边界、加总恒等式、压力方向、相同起点与相近提前期；保留朴素比较基准
添加新行业先定义需求主体、目标、单位、供需边界，再补本行业机制、数据、适配器、经营映射和验证；不能只替换表头或行业名称

更新到新的信息截止日尤其要处理

新能源当前 run_full.py 明确限制2026-11-03及2025为最近完整历史年。更新时先核验新发布数据、税费规则和2028等后续政策，再调整相应校验与配置；不要为让程序通过而直接删掉日期检查。

ABS来源记录及可选工作簿导入器含本案例2026年9月简报的日期与核验状态；更新数据不能沿用成已核验的新来源。当前第4—15、第16—27月回测窗口对应最后实际月2026年9月；末期变动后，应重新计算与目标日历年对应的提前期，不能仍称旧窗口匹配新计划。

ABS当前适配器要求规模和计划数均为正，遇到零新增月份会拒绝运行。扩展到稀疏备案细分前，需要单独设计零值、单均规模和降级策略，不能把缺数填成零或为过校验填成小正数。

两模块的代表车型、税基、持有期、单项工时等示例不是行业实测平均值。取得新的实际参数时记录来源和性质，并重新检查转换、覆盖与适用范围。

可复用的运行与交付命令

在仓库根目录执行，路径使用新的目录名：

python demand-forecast/scripts/run_skill.py --industry nev --output-dir output/nev-my-change
python demand-forecast/scripts/run_skill.py --industry abs --output-dir output/abs-my-change
python -m unittest discover -s demand-forecast/scripts -p "test_*.py"
python tools/check_delivery.py
python tools/build_delivery.py

--demo用于明确标记的企业教学核算，--open用于自动打开报告。这里的命令是接手示例；数据、算法没有变化时不必反复运行全部模型来证明文字修改正确。

打包生成 dist/demand-forecast-skill-final.zip（完整课堂交付）与 dist/demand-forecast-skill-only.zip（纯Skill）。dist不进入Git版本跟踪，发布到GitHub时作为Release附件上传。不能只提交代码而漏掉其必需数据、配置或引用文件。

当前未要求把某人的私人邮箱或令牌写入项目。仓库为私有，现有运行数据已保留；需他人协作时由仓库拥有者授予对应访问权限，或直接分享完整包，不改变运行逻辑。

修改交接记录模板

• 修改人、分支／提交、项目版本、信息截止日。

• 原问题与目标决策；改动文件和证据来源。

• 数据是原始观测、差分、外部研究、规划假设还是企业教学值。

• 旧版／新版预测、分支误差及业务行动的变化；变化原因是否能解释。

• 实际做了哪些验证、尚未验证什么；是否有人用新案例独立跑通。

• 留给下一位的缺口、建议顺序和负责人，不把未完成项写成已通过。

建议下一步优先：补同口径更长历史与发布版本 → 补企业实际订单／管线和约束 → 补价格、利差、资产池、海外结构 → 检查新方法的增益 → 做真实前瞻跟踪与组员独立试用。
